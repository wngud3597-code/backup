## 2. 남은 브라우저 확인 — 계속 미확인

남은 핵심은 감독 보완 후 **최신 실제 브라우저 혼합 질문**, 원래 같은 탭 **A→B→A**, 그 과정의 답변별 구절/출처 복원과 rerun 중복·추가 호출 여부다. CLI 성공·AppTest·저장 결과 재생을 브라우저 성공으로 바꾸지 않는다.

짧은 수동 절차: 같은 정상 앱 탭에서 A 인터스텔라의 답변·근거·메시지 수를 기록 → B 더 문(2023)으로 전환하고 ID 753091 확인 → 최신 응답 확인을 실시할 때만 기존 혼합 질문을 한 번 제출하고 두 판정/구절 기록 → A로 돌아와 당시 답변·URL·복수 구절이 같은지 비교 → 근거 펼침·모드 변경·일반 rerun에서 중복 저장/생성이 없는지 확인한다. 완전 새로고침·새 탭·서버 재시작은 하지 않는다. 기존 A 기록이 없으면 사용자가 직접 한 번 질문해야 하며 추가 실제 호출이다.

구체적인 미완료 체크와 기록 항목은 [기존 한 곳의 체크리스트](PRESENTATION.md)에 둔다. 이번에는 위 절차·질문·브라우저 자동화를 실행하지 않았다. UI 변화만으로 호출이 없었다고 추정하지 말고 수행 시 서비스 호출 계수/로그를 함께 기록한다. 계수를 관측하지 못하면 그 부분은 미확인이다.

## 3. GMS 규약·공식 안내 조사 결과

프로젝트 규약은 [config.py](../movie_lab/config.py), [document_llm.py](../movie_lab/document_llm.py)의 `create_document_planner`를 확인했다. 기존 GMS 주소는 `https://gms.ssafy.io/gmsapi/api.openai.com/v1/`다. 기존 팩토리가 dotenv와 `GMS_KEY`를 읽어 생성한 클라이언트로 **GET models만** 요청했다. 키·환경변수 값·원시 오류 본문·헤더는 기록하지 않았다.

| 조사 | 실제 관측 | 판단 |
|---|---|---|
| 제한 환경 모델 목록 조회 | [기록](../artifacts/review_upgrade_preparation/gms_models.json): 연결 실패, HTTP 응답 없음 | 서버에 도달했거나 인증/모델을 검사했다고 판단하지 않음 |
| 네트워크 허용 경로의 동일 조회 | [기록](../artifacts/review_upgrade_preparation/gms_models_authorized.json): **HTTP 500**, SDK 자동 재시도 0, 0.645초 | `/models` 지원 여부·목록·새 모델 권한은 **미확인**. 500만으로 미지원·인증 성공/실패를 단정하지 않음. 추가 목록 재시도·개별 모델 조회·생성 요청 없음 |
| [GMS 공식 호스트](https://gms.ssafy.io/) 공개 첫 화면 | [인증 없는 GET 기록](../artifacts/review_upgrade_preparation/gms_official_entry.json): HTTP 200이나 제목은 ‘페이지를 찾을 수 없습니다’, 안내 링크 없음 | HTTP 200을 안내 확인 성공으로 보지 않음. 로그인 후 공식 모델/권한 안내는 확보하지 못함 |
| OpenAI 공식 문서 | 아래 모델/구조화 출력/목록 문서를 실제 열어 확인 | 원 공급자 문서의 설명이며 **GMS 프록시·계정 지원 증거가 아님** |

목록 조회는 총 두 클라이언트 시도였고 첫 시도는 연결 실패, 두 번째는 서버 500이었다. 별도 공개 화면 GET 1회가 있다. **새 생성·검토·임베딩 요청은 모두 0회**다. 조사 스크립트는 [inspect_gms_models.py](../artifacts/review_upgrade_preparation/inspect_gms_models.py)이며 기존 결과 파일이 있으면 자동 재호출을 거부한다.

OpenAI의 [목록 API](https://developers.openai.com/api/reference/resources/models/methods/list)는 모델 조회 경로를 설명하지만 GMS가 이를 노출해야 한다는 뜻은 아니다. 설령 목록에 ID가 나타나도 Chat Completions·JSON Schema·해당 옵션·실제 권한까지 확인한 것으로 취급하지 않는다. 블로그·다른 GMS 서비스의 문서를 SSAFY 공식 안내로 사용하지 않았다.

**실제 생성이 확인된 모델은 이전 기록의 `gpt-4o-mini`뿐**이다. 이번에는 그 연결을 재검사하지 않았다. 새로운 후보를 ‘현재 GMS에서 호출 가능’으로 확정할 근거가 없다. 다음 단계의 최소 선행 조건은 공식 GMS 허용 모델 안내 또는 정상 목록/권한 정보 확보와, 별도로 허용된 최소 생성·구조화 출력 검사다. 이번에는 생성 검사를 하지 않는다.

### 옵션 확인표

현재 [AnswerGenerator._request_impl](../movie_lab/answering.py)은 `temperature=0`, `max_tokens=1800`, strict `response_format=json_schema`, 비스트리밍 Chat Completions를 사용한다. 클라이언트 timeout은 25초·SDK 자동 재시도 0이며 코드의 제한 재처리는 별도다.

| 항목 | 후보에서 다음에 확인할 내용 |
|---|---|
| 실제 ID/권한 | alias와 서버 보고 ID, Chat Completions 사용 가능 여부. 목록 노출과 생성 성공을 따로 기록 |
| 구조화 출력 | 실제 일반 답변/항목별 검토 스키마와 `strict`, enum, 빈 인용을 지원하는지. OpenAI의 [구조화 출력 안내](https://developers.openai.com/api/docs/guides/structured-outputs)만으로 GMS 지원을 확정하지 않음 |
| JSON 대체 | 기존 코드 검증을 유지하는 일반 JSON 대체 가능 여부. structured/일반 JSON은 다른 조건으로 표시하고 조용히 섞어 점수 비교하지 않음 |
| 샘플링/출력 상한 | `temperature=0` 지원 여부, `max_tokens` 또는 `max_completion_tokens` 요구 여부, reasoning 토큰과 가시 출력의 상한 차이. 기존 호출 옵션을 그대로 보내도 된다고 가정하지 않음 |
| 추론 옵션 | 두 모델의 OpenAI 문서는 none/low/medium/high/xhigh를 설명하지만 GMS 전달 지원은 미확인. 비교에서는 공통으로 확인된 조건만 고정하고 차이가 있으면 설정 차이를 공개 |
| 오류/완료 상태 | refusal·빈 content·길이 종료·timeout·400/401/403/429/5xx를 분리하고 반복 재시도하지 않음. 검토 누락/중복 ID와 잘못된 관계도 현재 계약대로 보류 |

신규 모델의 옵션 어댑터나 역할별 설정 분리는 **아직 구현하지 않았다.** 옵션이 맞지 않으면 품질 실패와 분리해 호환성 미확인/실패로 기록한다.

## 5. 같은 질문·같은 근거의 역할별 비교 계획 — 미실행

### 입력을 먼저 고정한다

- 현재 모델 M0=`gpt-4o-mini`, 후보 M1/M2는 위 두 모델 중 GMS 접근이 확인된 것만 사용한다.
- 영화 ID·질문 원문·모드·동일 영화의 대화·원문 근거 텍스트·순서·scope·출처 번호·구절 분할·프롬프트/JSON Schema·감독 레지스트리·코드 버전을 고정하고 각각 SHA-256을 남긴다.
- **최종 표시용 `sources`만으로 문맥을 복원하지 않는다.** 기존 JSON의 `retrieval.sources` 원문을 읽어 같은 구절 ID를 만든다. `sources`는 최종 인용 후 축약/가공된 목록이므로 서로 다른 입력이 될 수 있다.
- 자료 준비·검색·임베딩을 다시 하지 않고 저장된 근거를 동결해 각 모델에 똑같이 제공한다. 캐시 갱신·새 수집·검색 개선과 모델 변경을 같은 실험에 섞지 않는다.
- 구조화 출력 방식·공통으로 지원되는 샘플링/출력 상한·재시도 상한을 고정한다. 공통 설정을 만들 수 없으면 엄밀한 같은 옵션 비교로 보고하지 않는다. 처음에는 생성/묶음 검토 각 1회, SDK 재시도 0으로 정해 재처리 효과를 분리한다.

### 원래 모델 출력과 코드 보완을 분리한다

각 사례는 다음 네 단계를 별도 열/원본으로 보관한다. 평가용 기록은 테스트 산출물이며 앱의 대화 저장 구조를 늘리지 않는다.

1. **원래 생성 출력:** HTTP 응답의 파싱 전 JSON/텍스트와 서버 보고 모델, 원래 facts/checks/citations. 감독 보완 전의 누락·근거 부족·잘못된 판정·정확한 구절 선택을 평가한다. 원시 헤더·키·오류 본문은 저장하지 않는다.
2. **코드 처리:** 감독 제안 전후, 기권 이유, 구절 매핑·원문 포함·번호·범위 검사 결과. 모델이 원래 맞힌 것과 코드가 보완한 것을 합산하지 않는다.
3. **항목별 검토:** 입력 claim_id/사용자 명제/이유/실제 구절, 관계와 이유 지지 응답, 코드의 수락·보류 이유. 일반 모드의 기존 검토 계약도 따로 유지한다.
4. **최종 서비스 결과:** 두 판정/근거·무인용 부족·부분 보류·호출 실패를 구분하고 과거 출처 스냅샷에 영향이 없는지 확인한다. 보완이 적용된 최종 성공을 생성 모델 자체의 정답으로 계산하지 않는다.

최신 Q2는 이미 **원래 초안 c1 근거 부족 → 코드의 상충 제안 → c1/c2 검토 수락**이었다. 이 기록을 모델의 원래 두 항목 정답이라고 바꾸지 않는다. 과거 기록에 파싱 전 일반 출력이 없으면 ‘원래 출력 미보존’으로 표시하고 후처리 결과를 원래 출력이라고 부르지 않는다.

### 답변 역할과 검토 역할을 따로 바꾼다

| 비교 | 바꾸는 것 | 고정하는 것 |
|---|---|---|
| 답변 역할 | 생성 모델 M0/M1/M2 | Q1~Q3 입력, 코드 보완, 검토 모델 M0 |
| 검토 역할 | 검토 모델 M0/M1/M2 | M0가 한 번 만든 동일 초안과 코드 처리 결과·항목별 인용. 후보마다 새 초안을 만들지 않음 |

두 후보가 모두 가능할 때 제안 실행 예산은 **생성 최대 9회·검토 최대 15회**다. 답변 역할 3×3의 생성/검토 9+9회, M0 초안에 후보 검토 2×3의 6회를 추가하고 공통 M0/M0 결과는 재사용한다. 부족 항목만 있거나 기계 검사에서 차단되면 검토를 건너뛰어 실제 수는 줄어든다. 이는 **미래 실행 계획의 상한**이며 이번 호출 수가 아니다. 지원 옵션 확인용 최소 요청은 별도 예산·결과로 먼저 제시해야 하고 이번에는 실행하지 않는다.

검토 정확성은 같은 모델의 ‘통과’ 자체를 정답으로 삼지 않는다. 사람이 고정 구절과 대조한 판정표를 먼저 만들고, 현재 실제/계약 사례의 **맞는 상충·잘못된 확인됨·맞는 확인됨·잘못된 상충**, 무관한 달 지형 인용, 현실 문서로 영화 장면 확인을 포함한 동일 고정 배치를 검토 모델 모두에 제공한다. 그 추가 의미 검토 실험은 위 24회 상한에 포함된 것이 아니므로, 필요하면 별도 최소 배치와 한도를 먼저 확정한다. 대체 응답 회귀와 실제 모델 오수락/오거부 측정은 구분한다.

### 기록과 완료 기준

기록 열은 `case_id/model_role/requested_model/reported_model/input_sha256/options/raw_output/director_proposal/mechanical_result/review_relation/reason_supported/final_decision/failure_stage`와 단계별 시간·실제 호출 수·캐시/고정 근거 재사용 여부다. token usage가 제공되면 원값을 남기되 GMS 가격 근거 없이는 비용을 확정하지 않는다. 생성·검토·코드 시간을 나누고 겹치는 generation_node를 다시 더하지 않는다.

- 동일 입력 해시와 옵션 차이를 확인하고 모델 원래 정답·코드 보완 효과·검토 오수락/오거부·최종 결과를 각각 비교해야 준비된 실험으로 인정한다.
- 잘못된 감독 판정/무관한 구절을 수락하는 것과 올바른 상충을 거부하는 것을 별도 실패로 기록한다. 보류 비율 감소만을 개선으로 삼지 않는다.
- API/옵션/스키마 실패는 모델 의미 정확도 실패와 분리한다. 400/401/403 또는 반복 서버/timeout이면 해당 역할에서 중단하고 전체 파이프라인을 재호출하지 않는다.
- 세 질문은 소규모 확인이며 광범위 정확도·실제 출처 충돌 판정·모델 일반 우열·평균 응답 시간을 확정할 자료가 아니다.
- 채택은 원래 초안의 누락/오판 개선, 검토 안전성 유지, 실제 지연/호출 부담을 함께 본 뒤 별도 결정한다. **현재는 후보 확정·기본값 변경·역할별 모델 연결·검색 개선 구현을 하지 않는다.**

조건 ID 선필터 비교는 [별도 질문집·완료 기준](DISCOVERY_UPGRADE_PLAN.md)을 따른다. 모델 비교와 독립적으로 진행해 개선 원인을 구분한다.
